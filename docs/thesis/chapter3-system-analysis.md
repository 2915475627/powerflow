# 第3章 系统分析

## 3.1 需求分析

### 3.1.1 功能需求

通过对工作流引擎典型应用场景的分析和目标用户群体的调研，本系统需要满足以下核心功能需求。

**工作流管理功能**。用户应当能够创建新的工作流，为其指定名称和描述；能够查看已创建的工作流列表，了解每个工作流的基本信息（名称、描述、节点数量、启用状态、创建时间）；能够编辑现有工作流的名称、描述和内容；能够删除不需要的工作流；能够将工作流标记为启用或禁用状态，只有启用的工作流才能被执行。

**节点编排功能**。系统需要支持六种节点类型的编排。START 节点作为工作流的唯一入口，不接收任何输入；END 节点作为工作流的终点，不产生任何输出。DATA_PROCESSING 节点负责数据处理和转换，通过 SpEL 表达式定义输入数据的变换逻辑，并将结果写入上下文。CONDITION 节点根据 SpEL 布尔表达式的求值结果决定执行路径的分支，实现动态条件路由。PARALLEL 节点作为并行分支的入口，通过它 fork 出多个执行路径，各路径之间相互独立、并发执行。JOIN 节点作为并行分支的汇合点，等待所有从属于同一 PARALLEL 节点的分支完成后再继续后续执行。

**DAG 可视化编辑功能**。用户应当在 Web 界面上直观地编辑工作流的节点图结构。系统应当支持从工具栏拖拽节点到画布上；支持在节点之间建立连线（通过拖拽节点的输出连杆到另一节点的输入连杆）；支持删除节点和连线；支持缩放画布和平移视图；支持选中节点后在配置面板中编辑其属性；支持在 CONDITION 节点的连线上标注条件表达式；不同类型的节点应当有不同的视觉样式，便于区分。

**工作流执行功能**。执行引擎是系统的核心，其需要完成以下工作：接收工作流执行请求和初始上下文数据；对工作流进行合法性校验，包括环检测（若存在环则拒绝执行）和起始节点存在性校验；按照 DAG 拓扑排序确定的顺序依次执行各节点；维护节点之间的数据传递，上游节点的输出通过映射规则传递给下游节点作为输入；执行过程中遇到节点失败应当立即停止并返回错误信息；成功执行的工作流返回最终上下文数据和完整的执行记录。

**上下文传递功能**。上下文（Context）是工作流执行过程中各节点共享的数据载体，以键值对的形式存储，支持嵌套结构（如 user.name）。每个节点通过 inputMapping 规定从上下文中的哪些键取值作为输入，通过 outputMapping 规定将输出写入上下文的哪些键中。这种声明式的映射机制使得节点之间的数据依赖关系清晰可见，也便于在不修改节点实现的情况下调整数据流向。

**条件路由功能**。CONDITION 节点通过 SpEL 表达式实现动态条件路由。每个 CONDITION 节点可以配置多条条件规则，每条规则包含一个 SpEL 布尔表达式和一个目标节点 ID。执行时，系统从上下文中提取必要的数据作为 SpEL 表达式的变量，对各规则顺序求值，第一个返回 true 的表达式所指向的节点即为下一跳；若所有表达式均为 false，则跳转到 defaultNextNodeId 指定的默认节点。

**并行分支功能**。PARALLEL 节点负责 fork 出多个并行执行分支。从 PARALLEL 节点出发的所有非 JOIN 目标节点构成一个并行组，各分支独立并发执行，彼此之间没有数据传递。JOIN 节点负责汇合与其配对的 PARALLEL 节点产生的所有并行分支。JOIN 节点等待所有分支完成后，收集各分支的输出汇总到上下文中，然后继续后续节点的执行。如果任意一个并行分支执行失败，JOIN 节点应当感知到失败状态并停止整个工作流的执行。

**执行日志功能**。系统应当完整记录每个工作流执行的详细信息，包括：执行 ID、触发时间、结束时间、执行状态（成功/失败）、总耗时；每个节点的执行详细信息：节点 ID、节点名称、执行状态、输入数据、输出数据、错误信息（若有）、执行开始时间、结束时间、耗时毫秒数。执行日志应当持久化到数据库中，支持按工作流 ID 或执行 ID 进行查询和回溯。

### 3.1.2 非功能需求

除了上述功能性需求之外，PowerFlow 系统还应当满足以下非功能性需求。

**可扩展性**。系统应当能够方便地支持新增节点类型。当需要添加一种新的节点类型时，开发者只需在 NodeExecutor 中增加对应的处理分支，或者在策略模式下新增一个策略类，而无需修改工作流执行引擎的核心逻辑、REST API 接口或持久化层。领域层的端口-适配器设计确保了新增节点类型不会对现有功能造成影响。

**可观测性**。执行引擎应当在每个节点的执行前后自动记录详细的日志信息，包括输入数据、输出数据、开始时间、结束时间、耗时毫秒数。这些日志通过 AOP 切面自动织入，无需在节点业务逻辑中显式编写，最大程度地降低了日志记录对节点执行性能的侵入。执行日志的完整记录为问题排查和性能分析提供了充分的数据支撑。

**性能需求**。排除节点自身的业务逻辑执行时间，单次工作流执行（不包含数据传输开销）的框架自身耗时应当控制在 100 毫秒以内。在 100 个节点规模的工作流下，从接收到返回执行结果的端到端延迟应当控制在 500 毫秒以内。Context 的读取操作在有 Redis 缓存命中的情况下应当控制在 1 毫秒以内。

**可靠性需求**。系统应当在执行前对工作流进行环检测，防止出现无限循环执行的情况。节点执行失败应当立即停止后续执行并返回有意义的错误信息。所有节点执行记录（包括失败节点的错误信息）均应持久化存储，确保执行历史的可追溯性。

### 3.1.3 用例分析

基于上述需求分析，本系统的典型用例场景如下。

**管理员创建工作流**。管理员登录系统后，点击"新建工作流"按钮，输入工作流名称和描述。进入 DAG 可视化编辑器，从工具栏拖拽 START 节点到画布，拖拽 DATA_PROCESSING 和 CONDITION 节点配置业务逻辑，拖拽 PARALLEL 和 JOIN 节点配置并行分支，最后拖拽 END 节点完成工作流设计。点击"保存"按钮，系统验证工作流合法性（节点连通性、无环等）后将工作流持久化到数据库。

**用户触发工作流执行**。用户在工作流列表页面选择某个已启用的工作流，点击"执行"按钮，在弹出的对话框中输入初始上下文数据（JSON 格式）。系统调用执行引擎完成工作流执行后，页面展示执行结果：最终上下文数据、各节点的执行状态和耗时数据。

**开发者测试单个节点**。开发者在节点测试页面选择目标工作流和目标节点，在左侧输入框输入测试上下文 JSON，点击"执行"按钮。系统调用节点执行器对目标节点进行独立求值，在右侧输出区域展示节点的输出结果、执行状态和耗时。该功能允许开发者在不触发完整工作流执行的情况下快速验证节点逻辑的正确性。

## 3.2 可行性分析

### 3.2.1 技术可行性

从技术角度分析，PowerFlow 系统所采用的核心技术均已非常成熟。Java 和 Spring Boot 生态历经十余年的工业验证，是构建企业级后端服务的首选技术栈之一，其依赖注入、AOP、声明式事务管理等能力为系统的架构设计提供了坚实的技术基础。DDD 六边形架构在业界已有大量成功实践，其解耦思想和端口-适配器模式非常契合工作流引擎这种领域逻辑复杂、外部依赖多样的场景。React 和 React Flow 为前端交互界面提供了成熟的组件化和图形编辑能力，尤其是 React Flow 项目在 GitHub 上拥有活跃的社区和详尽的文档支持。SpEL 作为 Spring 框架的内置组件，无需引入额外的第三方规则引擎依赖，降低了系统的整体复杂度。PostgreSQL 的 JSONB 数据类型使得关系型数据库可以直接存储和查询图结构数据，兼顾了结构化查询的便利性和文档存储的灵活性。综合来看，技术方案不存在难以突破的瓶颈。

### 3.2.2 经济可行性

从经济角度分析，PowerFlow 系统所使用的所有技术栈——Java（OpenJDK）、Spring Boot、React、React Flow、PostgreSQL、Redis——均为开源软件，无需支付任何软件许可费用。开发环境可以使用免费的 IDE（IntelliJ IDEA Community、Eclipse、VS Code），部署环境可以使用开源的容器化技术（Docker）和免费的云平台（GitHub Actions、Heroku 等）。系统的开发周期预计为 5 个子项目阶段，每个阶段聚焦于一个相对独立的子系统模块，可以利用课余时间分阶段迭代完成。总体经济成本可控。

### 3.2.3 操作可行性

从操作角度分析，PowerFlow 系统设计了直观的 Web UI 交互界面，用户通过浏览器即可完成工作流的创建、编辑、配置和执行，无需学习复杂的命令行工具或配置文件格式。节点测试功能允许开发者在不触发完整工作流的情况下独立验证节点逻辑，降低了调试成本和操作门槛。系统的功能模块划分清晰，用户角色（管理员、用户、开发者）的操作路径互不干扰。综合来看，系统具备良好的操作可行性。
